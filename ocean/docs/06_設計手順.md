# 06 設計手順 ─ 役の分け方と段階

## 一・役の原則

| 役 | 領域 | やる |
|---|---|---|
| **CC**（Claude Code） | 設計監査・正典の起草 | 仕様書、UI 設計書、配分、合格判定、ユタ語彙の補注、祭文の起草 |
| **Codex** | 弓編の堅牢化 ─ **場側** | 巫の loop、ガイス検証、ramp の rAF、言上の不滅、ws hub の堅さ、UI 実装 |
| **Cline** | 横断差し込み ─ **器側** | 各依代に葉 API を差し込む、接続灯、御願の到来表示 |

場と器の境界が役の境界。器の中の音色設計は Cline、器を場から動かす言葉は Codex、その間の規約は CC。
CC はコードを書かない（設計と判定のみ）。

### 段階 1（Cline L1+L2）─ 合格条件
- [stone-beats.html](../stone-beats.html) を `http://localhost:port/stone-beats.html` で開き、画面右下に**接続灯（緑）**が点く
- [ocean.html](../ocean.html) も同様
- field を開き、節の庭に二つの依代が現れる
- 各依代の `kehai` が 6Hz で流れる（マブイ計に動きがある）

### 段階 2（Codex C5）─ 合格条件
- [mock-instrument.html](../mock-instrument.html) を場に入れる
- field から `play / stop / setParam / ramp / loadPreset / snapshot` を一通り発火、すべて mock 側で受け取れる
- 言上に往復が記録される

### 段階 3（Codex C1-C4, C6）─ 合格条件
- hub: 6 クライアント同時接続でも詰まらない、切断時に綺麗に掃除される
- loop: 応答規則 `> < == 持続 一度 冷却` が境界値で正しく動く
- ramp: 揺らぎが招の時に焼かれる、競合は後勝ち
- 言上: `logs/YYYY-MM-DD.jsonl` に atomic に追記される
- スキーマ: 未知 target を含む祭文は読み込み時に拒否される

### 段階 4（CC・第一巻祭文）─ 合格条件
- [docs/07_祭文集.md](07_祭文集.md)（未起草）に第一巻が書かれる
- 楽器は stone-beats と ocean のみ
- 祭次・応答ともに人が一行で読める
- duration、target、command、param すべて schema 通り

### 段階 5（Codex・第一巻上演）─ 合格条件
- 祭文を field に読み込み、招を撃つ
- 祭次が時刻通りに走る（揺らぎ範囲内）
- 応答が条件通りに発火
- 沈黙時に「マブイグミ」が動く（人が押す or 自動）
- ヌジファとウクリで正しく止まる
- 言上が完全に残る

## 四・タスクの渡し方

CC は文書を書き、**[tasks/](../tasks/) 配下に小さな task ファイルを分けて投げる**：

```
tasks/
├ codex/
│   ├ C1_hub堅化.md
│   ├ C2_loop堅化.md
│   ├ C3_ramp堅化.md
│   ├ C4_言上不滅.md
│   ├ C5_mock試験.md
│   ├ C6_スキーマ検証.md
│   └ UI_*.md           ← UI 設計の各層
└ cline/
    ├ L1_stone-beats接続.md
    ├ L2_ocean接続.md
    ├ L3_geometry接続.md
    ├ L4_particle接続.md
    └ L5_blocker解消.md  ← 要ユーザ承認
```

各 task は**一画面で読める長さ**、構成は固定：

```
# タスク名

## 入力
- 何を読むか（仕様書・既存ファイルへのリンク）

## 出力
- 何を書くか（変更するファイル・新規ファイル）

## 合格条件
- 一行で書ける検証可能な条件

## 注意
- 触ってはいけないもの
- 期待される作法
```

Codex / Cline は task ファイルを一つずつ持って行き、完了したら **CC が監査**する。
CC は監査のみで実装はしない。

## 五・原則の確認

1. **CC は実装に踏み込まない** ─ 文書と判定で関与する
2. **Codex / Cline は CC の文書通りに動く** ─ 文書に無いことはやらない
3. **語と所作は CC が決める** ─ Codex / Cline が変えない
4. **音色設計は Cline、儀礼は Codex** ─ 境界を越えない
5. **ユーザ承認が要るもの**（clone、push、外部デプロイ）は必ず止まる

CC は最大品質を出すため、文書の質と判定の厳しさで貢献する。実装の手数はリミットの中で Codex / Cline に任せる。
